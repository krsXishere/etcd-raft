### 3.X Implementation Details

**Programming Language.** The system is implemented in Go (version 1.23), selected for its first-class concurrency primitives — goroutines and channels — which align naturally with the concurrent, event-driven structure of consensus protocols. Each node's election ticker, heartbeat broadcast, and RPC dispatch execute as independent goroutines coordinated through channels and mutexes, enabling efficient multiplexing without the overhead of OS-level threads. Go's standard library for networked services (`net/http`, `encoding/json`) and its compilation to a single statically linked binary further simplify deployment in distributed environments.

**Consensus Engine.** Rather than integrating an existing library such as `etcd/raft` or `hashicorp/raft`, the prototype employs a custom lightweight Raft implementation tailored to the requirements of this study. The module covers leader election, log replication via single-entry AppendEntries RPCs, and commit-index advancement, while intentionally omitting features orthogonal to the research objective — namely snapshots, dynamic membership changes, and durable persistent storage. This design choice provides full control over the timing parameters (election timeout and heartbeat interval) without requiring modification of a third-party library's internal state machine. Crucially, the safety invariants of Raft — term-based voting, log-matching, and leader completeness — are preserved without alteration; only the timing configuration is subject to adaptive control.

**Adaptive Controller Module.** Each node runs a local PID (Proportional–Integral–Derivative) controller that dynamically adjusts the election timeout in response to observed network round-trip times. The control law computes the error as the deviation of the measured RTT from a configured baseline and produces a corrected timeout:

$$T_{\text{election}} = \text{clamp}\!\Bigl(T_{\text{base}} + K_p \cdot e + K_i \!\int\! e\,dt + K_d \cdot \frac{de}{dt},\; T_{\min},\; T_{\max}\Bigr)$$

The integral term employs back-calculation anti-windup: when the raw output would exceed the bounds $[T_{\min},\, T_{\max}]$, the integrator is adjusted so the output sits exactly at the violated bound, preventing sluggish recovery after saturation. The derivative term is smoothed with a first-order low-pass filter ($\alpha = 0.3$) to suppress high-frequency measurement noise. The heartbeat interval is derived deterministically as $T_{\text{heartbeat}} = T_{\text{election}} / R$, where $R$ is a configurable ratio (default $R = 5$), preserving the timing relationship assumed by the Raft protocol. Per-peer RTT samples are maintained in fixed-size sliding windows, and the moving average is fed to the controller on each update cycle.

**Observability Stack.** Each node exports runtime metrics via the Prometheus client library for Go (`client_golang`). Exported metrics include per-peer RTT (both as an instantaneous gauge and as a histogram for percentile analysis), current election timeout, heartbeat interval, PID controller error and derivative terms, the node's Raft role (encoded both numerically and as a labeled indicator), current term, and event counters for role transitions and leader elections. A Prometheus instance scrapes these endpoints at a configurable interval, and a Grafana dashboard provides real-time visualization of adaptation behavior — enabling direct observation of how the controller adjusts timing parameters in response to network condition changes across all five nodes simultaneously.

**Deployment Environment.** The system is deployed as a five-node cluster in which each node executes an identical compiled binary, differentiated only by its node identifier, listen port, and peer address configuration supplied via command-line flags. Nodes communicate over a logical full-mesh topology using synchronous HTTP-based RPCs with JSON-encoded message envelopes. For experimental evaluation, nodes are deployed on separate cloud instances (e.g., AWS EC2 free-tier) to introduce realistic, heterogeneous network latencies; the system is equally runnable on a single host for development using the provided cluster launch script. Containerized deployment via Docker is supported for reproducibility.
